# 0.7.2：真实 OCR 模型流式输出

用户报告：整页识别完才模拟逐字回放；要求模型生成正文时直接实时渲染，并调查 CPU 速度。

## 原因与修改

原生后端的 MNN `response` 本来写入逐步输出流，但外围 `ostringstream` 只在区域结束后取出结果，公共进度事件没有正文。页面随后对最终结果做字符回放。

Android 自有 `AndroidGenerationStream` 直接接收模型写入，按作业／requestId／attempt 更新累计正文；重试替换当前区域，UTF-8 尾部半个字符等待后续字节，不丢掉原始字节。快照独立于有限长度的进度事件队列。实际 App JNI 使用标准 UTF-8 转为 Java String，`recognitionStatus` 携带模型快照；活跃页面约 150ms 刷新，生成期间可以阅读。终态直接显示完整保存结果，手动回放和 JSON 示例仍可使用。

未闭合表格／公式显示实时原文，区域完成后排版。保存前不校对、排序、导出；最终图片资源与 DocumentIR 保持已有保存流程。区域流对象在作业销毁时清理；实时正文不反复写入持久文档。生产源码适配仍通过精确替换生成；相邻 docprase/MNN 源码没有修改。

## 速度判断

当前实际固定配置是 CPU 单线程，区域串行；Android 的 OpenCL/Vulkan/OpenGL 均关闭。桌面样图的生成尝试累计视觉约4.05s、prefill约14.71s、decode约2.99s，主要时间在视觉输入与生成前准备。页面等待完整结果是独立的展示延迟，接通流式不会免除模型的计算时间。

每个区域的快照和 Android `OcrEngine` 日志记录首内容、视觉、prefill、decode、输出token数与总耗时。CPU 配置值得进一步测量，但平板芯片、内存带宽、温度、线程数与可用后端影响需要真机对比；本轮没有把桌面诊断秒数当作平板性能，也没有未经验证修改默认线程／GPU。
