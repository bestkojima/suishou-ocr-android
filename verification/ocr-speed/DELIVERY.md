# 0.7.3：模型复用与 CPU 线程提速

用户反馈识别太慢，怀疑每个区域都重新加载模型。本轮检查和修改针对实际模型计算与引擎生命周期，不修改回放字符速度。

## 已确认的行为

区域之间的 `Llm::reset()` 只清空上下文、输出／历史 token 和 KV 状态，不卸载模型。视觉处理与 prefill 仍需针对每张裁剪图执行。0.7.2 的 `RecognitionController` 在每张图 finally 中销毁引擎，导致下一张再次加载，也失去已经准备好的运行缓存；这个生命周期已修改。

## 实施

- 每张图完成只释放作业、结果和流式快照，保持模型加载；下一张直接复用。
- 真正的 CPU 线程变化、模型下载／删除时卸载；自动与显式设置得到相同有效线程时保留模型。
- 内存压力和退出 Activity 时由同一推理 executor 请求释放；活跃作业不被并发销毁，卸载失败保持占用，提示重启。
- 默认自动选择1／2／4，最多4且受可用CPU限制；模型页可选择。Java发出实际配置，Android ABI将计划传到版面、语言、视觉后端和错误恢复路径；manifest／profile／流式快照／日志记录实际线程数，mmap标记也校准为true。
- 区域保持串行、会话保持隔离。没有跨区域盲目复用KV，没有降低分辨率、token预算或更换模型，GPU仍关闭。

## 实际模型对比

同源Linux x86_64 VirtualBox、4个逻辑处理器，同一真实样图。探索配置顺序运行，每次创建一个引擎并连续识别两张相同图片；加载和模型身份校验在识别计时外。秒数不是Android设备性能。

| 配置 | 新引擎首次整页 | 连续第二张整页 |
| --- | ---: | ---: |
| CPU 1线程 | 23.15s | 22.03s |
| CPU 2线程 | 22.49s | 14.63s |
| CPU 4线程 | 23.02s | 11.22s |
| 语言4、视觉1（未采用） | 25.32s | 14.25s |

各次Markdown的SHA-256完全一致。最终代码的区域类型、几何、状态、正文与单线程结果一致。4线程首次仍需初始化，首次内容等待更长，不能将连续识别收益称为首次提速。视觉单线程没有改善首次等待且连续识别更慢，未采用。

最终代码复验：一个引擎连续三次，整页24.12s、12.80s、11.20s；后两次加载耗时为0，运行不再创建引擎。该复验同时执行页面回归，冷热数据分开保留。连续两次中位数约12.00s，相对单线程连续样图约减少45.5%。各次真实流式输出都在同步run和区域完成前可读；流式原文与最终保存的模型attempt输出一致。见 `performance.json`、各配置的 `benchmark.json`／`timeline-*.json`／原始日志和 `final-4/manifest-*.json`。
